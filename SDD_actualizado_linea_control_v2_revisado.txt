SDD - SISTEMA WEB PARA EL CONTROL DE TURNOS Y SEGUIMIENTO DE RUTAS
VERSIÓN ACTUALIZADA

1. OBJETIVO
Este documento define la arquitectura, diseño técnico y reglas principales del sistema
web para el control de turnos y seguimiento de rutas, desarrollado con Laravel MVC y
una API REST para la aplicación móvil.

El sistema complementa el sistema existente de la empresa, concentrándose en la
ubicación GPS, ejecución del turno, control del recorrido y visualización de micros.

2. ARQUITECTURA
- Backend: Laravel MVC.
- Aplicación móvil: consume API REST.
- Base de datos: almacena usuarios, parametrización, asignaciones y seguimiento.
- WebSockets/Reverb: únicamente para comunicar al panel web las nuevas posiciones
  de los micros y visualizarlas en el mapa.
- Almacenamiento local móvil: permite conservar posiciones cuando no existe Internet.

Flujo general:

APP MÓVIL
  -> GPS
  -> API HTTP periódica
  -> Laravel
  -> SeguimientoGps
  -> ControlRecorrido
  -> Evento WebSocket
  -> Dashboard / mapa en vivo

4. USERS, CONDUCTORES, PROPIETARIOS Y ROLES
La autenticación utiliza Users y la administración de roles utiliza Spatie Permission.

Relaciones:

users 1 ---- 0..1 conductores
users 1 ---- 0..1 propietarios

Un mismo usuario puede tener ambos perfiles y ambos roles.

Los datos comunes de autenticación/contacto permanecen en users cuando corresponda.
Las tablas conductor y propietario contienen datos específicos de cada función.

Ejemplo:
conductores:
- id
- user_id
- licencia
- carnet
- estado

propietarios:
- id
- user_id
- carnet
- estado
- fecha_registro

Un usuario sin rol no debe acceder a funcionalidades que requieran un rol
operativo. Un administrador puede asignar posteriormente el rol correspondiente.


5. PARAMETRIZACIÓN
Se consideran principalmente parametrización:
- turno
- ruta
- parada
- ruta_parada
- micro
- interno

Turno solamente identifica:
- mañana
- tarde
- noche

Turno no representa el estado de ejecución.

RutaParada define la ruta esperada y el orden de sus paradas. No se modifica cada vez
que un micro realiza un recorrido.

Conceptualmente:
RutaParada = lo que debería ocurrir.
SeguimientoGps = lo que realmente ocurrió.
ControlRecorrido = resultado de comparar ambos.


6. ASIGNACION_TURNO
Representa el registro de una operación diaria de servicio y no solamente una
selección de turno.

Campos:
- id
- fecha
- turno_id
- ruta_id
- micro_id
- conductor_id (pendiente de confirmar si la relación conductor-micro será fija)
- hora_salida
- hora_llegada
- estado
- observaciones
- timestamps

Estados:
- pendiente
- en_curso
- completado   (CORREGIDO: la migración real de asignacion_turnos usa
                "completado", no "culminado". Se documenta aquí con el
                valor real para no forzar una migración de datos y no
                romper las validaciones/vistas ya escritas. Si el
                cliente insiste en el término "culminado" a nivel de
                negocio, se resuelve como una etiqueta de presentación
                (accessor estadoBadge), no como el valor real de la
                columna.)
- retrasado    (CORREGIDO: existe en la migración real y tiene valor de
                negocio propio -distinto de cancelado-, no se elimina.)
- cancelado

Flujo:
pendiente -> en_curso -> completado
                       -> retrasado (evento intermedio, no bloquea llegar a completado)

hora_salida se registra al iniciar.
hora_llegada se registra automáticamente al detectar la culminación del recorrido
de ida y vuelta.


7. CREACIÓN DE ASIGNACION_TURNO
Debe realizarse desde AsignacionTurnoService mediante DB::transaction().

Proceso:
1. Forzar estado = pendiente.
2. Validar turno existente y activo.
3. Validar ruta existente y activa.
4. Validar micro existente y activo.
5. Validar conductor existente y activo.
6. Validar disponibilidad.
7. Crear asignacion_turno.
8. Si todo es correcto -> COMMIT.
9. Si falla una operación crítica -> ROLLBACK.

La tabla realmente modificada al crear es:
- asignacion_turnos: INSERT.

Las demás tablas participan como consulta.


8. INICIO DEL TURNO
No se crea inicialmente una tabla InicioTurno.

Es una operación sobre AsignacionTurno:

pendiente
  -> en_curso
  -> hora_salida = hora actual del servidor

Endpoint:
POST /api/mis/asignaciones/{id}/iniciar

Validar:
- usuario autenticado;
- usuario corresponde al conductor;
- asignación pertenece al conductor;
- estado pendiente.

Modifica:
- asignacion_turnos.


9. SEGUIMIENTO GPS
SeguimientoGps registra las posiciones reales recibidas del dispositivo.

Campos:
- id
- asignacion_turno_id
- fecha_hora_gps
- latitud
- longitud
- velocidad
- fecha_hora_sincronizacion
- timestamps

fecha_hora_gps = momento en que ocurrió la posición en el dispositivo.
fecha_hora_sincronizacion = momento en que el servidor recibió/sincronizó el registro.

Endpoint:
POST /api/mis/asignaciones/{id}/ubicaciones

Flujo:
GPS -> envío periódico HTTP -> Laravel -> SeguimientoGps.


10. CONTROL_RECorrido
ControlRecorrido evalúa una posición GPS respecto de la ruta y las paradas
esperadas.

Campos:
- id
- asignacion_turno_id
- seguimiento_gps_id
- ruta_parada_id
- fecha_hora
- estado
- observacion
- timestamps

Estados:
- pendiente
- cumplido
- omitido
- fuera_ruta

ControlRecorrido NO captura directamente el GPS.
La captura corresponde a:
GPS -> API -> SeguimientoGps.

ControlRecorrido utiliza el registro GPS como evidencia para evaluar el recorrido.


11. CONTROL DE POSICIÓN
Se propone una función de negocio en ControlRecorridoService, por ejemplo:

controlarPosicion(asignacionTurno, latitud, longitud, fechaHora)

Debe:
1. obtener la ruta de la asignación;
2. obtener la secuencia RutaParada;
3. determinar la siguiente parada esperada;
4. calcular la distancia entre GPS y la parada;
5. aplicar una tolerancia geográfica;
6. comprobar la secuencia;
7. registrar el resultado cuando corresponda;
8. detectar posibles posiciones fuera de ruta;
9. contribuir a determinar la finalización de ida y vuelta.

No basta con:
"GPS dentro del radio = parada cumplida".

Debe considerarse también el orden de las paradas.

Ejemplo:
A -> B -> C -> D

Si B es la siguiente parada esperada y el GPS aparece cerca de C, no se debe marcar
C automáticamente como cumplida. Debe evaluarse la secuencia.

Tampoco debe declararse una parada omitida por una sola lectura que no caiga en su
radio, porque el micro pudo haber pasado por ella entre dos muestras.


12. CONTROL DE IDA Y VUELTA
La parametrización debe permitir identificar el recorrido de ida y el de vuelta.

Flujo:
AsignacionTurno
 -> paradas de ida
 -> última parada de ida
 -> paradas de vuelta
 -> última parada de vuelta
 -> culminación

La regla exacta de transición entre ida y vuelta debe confirmarse según la
parametrización real del cliente.


13. CULMINACIÓN AUTOMÁTICA
La finalización normal será determinada por ControlRecorrido.

Cuando se confirme que se completó el recorrido de vuelta:

UPDATE asignacion_turnos
SET estado = 'culminado',
    hora_llegada = NOW()

El conductor no debe ser la única fuente para determinar la culminación.

Puede mantenerse una operación de contingencia administrativa, pero el flujo normal
será automático.


14. FUERA DE RUTA
Si la posición no corresponde razonablemente al recorrido esperado, puede registrarse:

estado = fuera_ruta

La evaluación debe considerar:
- ruta;
- RutaParada;
- secuencia;
- posición GPS;
- tolerancia;
- posiciones consecutivas.

Una posición aislada no debería producir automáticamente una sanción.


15. WEBSOCKETS / VISUALIZACIÓN EN TIEMPO REAL
Los WebSockets se utilizan exclusivamente como mecanismo de comunicación para que el
panel web reciba las nuevas posiciones del micro sin tener que consultar
continuamente la base de datos.

WebSocket NO:
- captura GPS;
- guarda GPS;
- controla paradas;
- determina fuera de ruta;
- culmina turnos.

WebSocket SÍ:
- recibe el evento de nueva posición;
- actualiza el marcador del micro en el mapa.

Flujo:

Móvil
 -> POST ubicación
 -> Laravel
 -> guardar SeguimientoGps
 -> evaluar ControlRecorrido
 -> emitir UbicacionMicroActualizada
 -> Reverb/WebSocket
 -> Dashboard
 -> actualizar marcador


16. POLLING Y WEBSOCKETS
El envío periódico de posiciones desde el móvil utiliza HTTP/API.

Los WebSockets se utilizan para transmitir esas posiciones al dashboard.

Si el WebSocket del dashboard falla, puede utilizarse polling como mecanismo de
respaldo para consultar la última ubicación disponible.

La pérdida total de Internet del móvil NO se resuelve con WebSocket ni con polling.
Para ello se utiliza almacenamiento local y sincronización posterior.


17. FUNCIONAMIENTO OFFLINE
Sin Internet:

GPS

Cuando vuelve Internet:

pendientes locales

 -> marcar localmente como sincronizado

Debe conservarse fecha_hora_gps original.

21. TRANSACCIONES
Las operaciones críticas de escritura deben utilizar DB::transaction() cuando se
necesite garantizar atomicidad.

Ejemplo:
DB::transaction(function () {
    guardarSeguimientoGps();
    evaluarControlRecorrido();
});

Si falla una operación incluida en la transacción, se ejecuta rollback de las
operaciones incluidas en ese bloque.

No confundir:
- transacción de BD;
- endpoint HTTP;
- WebSocket;
- parametrización.

Los estados de negocio como fuera_ruta, omitido o retrasado no son errores de BD y
no deben provocar rollback por sí mismos.

24. DECISIONES PENDIENTES
Antes de cerrar definitivamente el modelo entidad-relación deben confirmarse:

1. Si conductor_id permanece en asignacion_turnos o si la relación conductor-micro
   será fija.
2. Si un conductor puede ser también propietario.
3. Si la relación conductor-micro cambia o es permanente.
4. Cómo se identifica exactamente ida y vuelta.
5. Radio geográfico para una parada.
6. Algoritmo para determinar una parada omitida entre dos lecturas GPS.
7. Criterio definitivo para fuera_ruta.
8. Frecuencia de envío GPS.
9. Tiempo máximo sin comunicación antes de generar una alerta.
10. Fuente exacta del GPS y posible integración con el sistema existente.

26. VERIFICACION CONTRA EL REPOSITORIO REAL Y DEFECTOS DETECTADOS
===============================================================================
Esta sección se agrega tras comparar el documento anterior con el codigo
real de pAvArDuwu/linea57_control. Cada punto es un defecto o riesgo que
debe resolverse ANTES o DURANTE la implementación, no después.

26.1 Estados de AsignacionTurno
Corregido en la sección 6. El documento decía "culminado" y no incluía
"retrasado"; la migración real usa "completado" y sí incluye "retrasado".
Se deja "completado"/"retrasado" como valores reales de la columna para
no forzar una migración de datos ni reescribir las validaciones y vistas
que ya dependen de esos valores.

26.2 Endpoint de finalización manual ausente
La sección 13 exige una operación de contingencia administrativa para
cuando la culminación automática (via ControlRecorrido) no se dispara.
El listado de endpoints de la sección 18 no la incluía. Se agrega:

POST /api/mis/asignaciones/{id}/finalizar   (conductor, uso normal)
POST /api/asignacion-turnos/{id}/forzar-culminacion (web, solo admin,
     uso de contingencia cuando el flujo automático no cerró el turno)

26.3 Infraestructura de WebSocket/Reverb no instalada
composer.json no tiene laravel/reverb ni pusher; package.json no tiene
laravel-echo. Todo el flujo de la sección 2, 15, 16 y 17 requiere,
además del código de negocio:
- composer require laravel/reverb
- php artisan install:broadcasting
- routes/channels.php con la definición del canal y su autorización
- npm install laravel-echo (cliente en resources/js)
- variables de entorno REVERB_* y BROADCAST_CONNECTION=reverb
Ninguno de estos pasos existe hoy en el repositorio.

26.4 VULNERABILIDAD: autorización del canal de posiciones
El documento no especifica si el canal por el que viaja
UbicacionMicroActualizada es público o privado. Un canal público
expondría la posición en vivo de cada micro/conductor a cualquiera que
conozca la URL del WebSocket, sin autenticación. Esto es un dato
sensible (permite rastrear a una persona). Debe ser un canal PRIVADO:

Broadcast::channel('dashboard.posiciones', function ($user) {
    return $user->hasAnyRole(['administrador', 'despachador']);
});

Y el evento debe implementar ShouldBroadcast (o ShouldBroadcastNow solo
si se acepta el costo de latencia sincrónica) sobre ese canal privado,
nunca sobre un canal public.

26.5 VULNERABILIDAD: ingesta de GPS sin límites
Ni /ubicaciones ni /ubicaciones/sincronizar tienen, en el diseño actual:
- throttling (un dispositivo con bug, o un actor malicioso con el token
  robado, puede enviar miles de puntos por segundo);
- límite de tamaño de lote en /sincronizar (un payload de 50.000 puntos
  bloquearía el worker/proceso PHP);
- validación de que fecha_hora_gps no sea futura más allá de un margen
  de tolerancia de reloj (evita que alguien falsifique el momento de un
  evento para simular una culminación temprana);
- una restricción de unicidad que evite duplicar el mismo punto si el
  cliente reintenta un envío que sí llegó a guardarse.

Mitigaciones a incorporar en UbicacionGpsRequest y en las rutas:
- Route::middleware(['auth:sanctum', 'throttle:120,1'])
- 'ubicaciones' => ['required','array','max:300'] en el request de
  sincronización masiva
- regla custom: fecha_hora_gps <= now()->addMinutes(2)
- índice único (asignacion_turno_id, fecha_hora_gps) en seguimiento_gps

26.6 Cardinalidad SeguimientoGps <-> ControlRecorrido sin cerrar
La sección 19 dejaba "según el modelo definitivo" la relación entre
ambas tablas. Esto debe cerrarse antes de escribir la migración porque
define si seguimiento_gps_id en control_recorrido es nullable() o no.
Recomendación: 1 SeguimientoGps puede originar como máximo 1
ControlRecorrido (la evaluación de una posición contra la ruta genera
un resultado), por lo que seguimiento_gps_id debe ser NOT NULL con
constrained()->cascadeOnDelete(). Si más adelante se necesita reevaluar
una misma posición contra varias paradas candidatas, se abre una
segunda relación explícita, no se reutiliza esta con nullable.

26.7 Autorización dispersa en vez de Policy
El diseño repite en varios controllers (iniciar, ubicaciones, finalizar)
la misma comprobación "¿esta asignación pertenece al conductor
autenticado?". Se centraliza en una Policy:

App\Policies\AsignacionTurnoPolicy::verGps(User $user, AsignacionTurno $a)
App\Policies\AsignacionTurnoPolicy::operar(User $user, AsignacionTurno $a)
    return $user->conductor?->id === $a->conductor_id;

Y los controllers solo llaman a $this->authorize('operar', $asignacion).
Esto es más testeable y evita que una futura ruta nueva se olvide de la
validación.

26.8 Afirmación desalineada sobre Form Requests
La sección 3 declaraba como hecho que los Controllers "usan Form
Requests". Verificado en el repositorio: hoy AsignacionTurnoApi y
AsignacionTurnoController validan con $request->validate([...]) inline,
no existen StoreAsignacionTurnoRequest ni UpdateAsignacionTurnoRequest.
Se corrige el estado a "pendiente" (ver FASE 3-bis en sección 22) y se
recomienda extraerlos al implementar los cambios de esta versión, para
que la afirmación de la sección 3 sea cierta cuando el sistema esté en
producción.

26.9 Riesgo de turno "colgado" (culminación automática)
Si la culminación depende exclusivamente de que ControlRecorrido detecte
el cierre de la vuelta, una falla silenciosa (GPS cortado, excepción no
capturada en el job) deja la asignación en_curso indefinidamente, sin
que nadie se entere. Se eleva de "decisión pendiente" a requisito
mínimo: un Job programado (Laravel Schedule, cada 15-30 min) que marque
como retrasado o dispare una alerta administrativa toda asignación
en_curso sin un registro en seguimiento_gps en los últimos N minutos
(N configurable, sugerido 10-15).

27. CUMPLIMIENTO MVC — VERIFICACION
===============================================================================
Se verifica capa por capa contra el diseño propuesto en esta versión:

Controllers: CUMPLE en diseño (reciben, delegan a Service, devuelven
respuesta). Hoy en código real NO cumple del todo porque valida inline
en vez de usar Form Requests (ver 26.8). Se corrige al implementar.

Services: CUMPLE. Toda regla de negocio (disponibilidad, secuencia de
paradas, ida/vuelta, culminación) vive en Services, nunca en el
Controller ni en la vista.

Models: CUMPLE. Son solo entidades Eloquent con relaciones y accessors
de presentación (estadoBadge, turnoEmoji); no contienen reglas de
negocio con efectos colaterales.

Views: CUMPLE en el diseño de la sección 3 (sin consultas ni reglas).
Se refuerza en la sección 28 con el rediseño de la vista de turnos.

Events/Broadcasting: capa nueva. Regla de arquitectura: un Event solo
transporta datos (payload) y define broadcastOn()/broadcastAs(); nunca
contiene lógica de negocio. La decisión de qué evaluar (cumplido,
omitido, fuera_ruta) ya se tomó en el Service ANTES de crear el Event;
el Event solo comunica el resultado ya calculado.

Regla de disparo (aplica igual que en la notificación push del backend
móvil): el evento se despacha DESPUES del commit de la transacción de
BD, nunca dentro de ella, y su clase implementa ShouldQueue para no
bloquear el request HTTP de ingesta de GPS, que se repite cada pocos
segundos por cada micro activo.

29. GUIA DE MANEJO DE ERRORES
===============================================================================
Regla general: distinguir error de sistema (BD caída, excepción no
prevista) de evento de negocio (fuera_ruta, retrasado, omitido). Solo el
primero es un "error" en el sentido de logging/alertas.

Codigo HTTP  Causa                                Accion
400          payload malformado                   Form Request rechaza,
                                                    mensaje especifico
                                                    por campo
403          conductor intenta operar una          AsignacionTurnoPolicy,
             asignacion que no es suya             $this->authorize()
404          asignacion/turno/ruta/micro/          findOrFail estandar
             conductor no existe                   de Laravel
409          conductor u micro ya ocupado en        ValidationException
             esa fecha/turno (conflicto de          personalizada dentro
             negocio, no error de servidor)         del Service
422          regla de negocio violada (turno        ValidationException::
             inactivo, estado invalido para la      withMessages()
             transicion solicitada)
429          exceso de peticiones de GPS            middleware throttle,
             (posible dispositivo con bug o         respuesta estandar de
             token comprometido)                    Laravel
5xx          excepcion no controlada               Log::error con
                                                    contexto (asignacion_
                                                    id, conductor_id),
                                                    NUNCA exponer el
                                                    stacktrace al cliente
                                                    movil

Reglas especificas:
- Los eventos de negocio (omitido, fuera_ruta, retrasado) se registran
  con Log::info o una tabla de auditoría, nunca con Log::error ni
  generan una alerta de sistema; son datos operativos esperados.
- Un fallo al notificar (push) o al emitir el evento WebSocket NUNCA
  revierte ni bloquea la escritura de datos que ya se guardó
  correctamente (seguimiento_gps, control_recorrido, asignacion_turnos).
  Se registra en failed_jobs y se reintenta segun la politica de colas
  de Laravel, de forma independiente a la respuesta HTTP ya enviada.
- En /ubicaciones/sincronizar, si el lote trae 50 puntos y uno tiene un
  dato invalido, se aceptan los 49 validos y se informa cuáles fueron
  rechazados y por qué, en vez de fallar el lote completo (evita perder
  datos GPS reales por un solo registro corrupto).
- DB::transaction() se usa solo para el conjunto minimo de escrituras
  que deben ser atomicas entre sí (ej. INSERT seguimiento_gps + INSERT
  control_recorrido cuando corresponde). No se usa para envolver
  llamadas a servicios externos (FCM, Reverb) ni para operaciones de
  solo lectura.

30. INTERFAZ WEB — REDISEÑO DEL TABLERO DE ASIGNACION DE TURNOS
===============================================================================
Se evaluó el mockup de referencia (tablero tipo Gantt, panel de detalle,
tarjetas de estadísticas, lista de incidencias) contra la vista actual
del repositorio (resources/views/asignacion_turno/index.blade.php), que
hoy es una tabla Bootstrap paginada.

30.1 Qué se adopta del mockup y por qué
- El cambio de tabla plana a TABLERO POR UNIDAD (tipo Gantt/línea de
  tiempo): responde directamente a la pregunta operativa real del
  despachador ("¿qué unidad está libre a tal hora?"), que una tabla
  paginada no resuelve bien. Este es el valor real del mockup y se
  traslada 1:1 conceptualmente.
- El PANEL DE DETALLE lateral que se actualiza al hacer clic en un
  turno, en vez de navegar a otra pantalla (show.blade.php). Reduce
  clics para la tarea más frecuente (revisar quién y con qué unidad).
- Las TARJETAS DE ESTADISTICAS arriba (turnos cubiertos, conductores
  libres, unidades en ruta, incidencias abiertas) como resumen ejecutivo
  de un vistazo.
- La LISTA DE INCIDENCIAS lateral, útil para que el despachador vea de
  inmediato qué requiere su atención sin filtrar la tabla.

30.2 Qué NO se adopta tal cual, y por qué
- La paleta y las fuentes del HTML enviado (Barlow Semi Condensed,
  IBM Plex Mono, variables --guindo-*/--azul-*) NO se importan tal
  cual. El proyecto ya tiene una identidad definida en
  resources/views/layouts/app.blade.php: --primary:#0B3C78 (azul) y
  --accent:#7B1E2B (guindo), que son prácticamente los mismos tonos.
  Traer una segunda paleta y dos familias tipográficas nuevas crearía
  dos sistemas de diseño conviviendo en la misma aplicación (esta
  pantalla se vería distinta a Conductores, Rutas, Micros, etc.).
- Los íconos SVG dibujados a mano del mockup NO se copian; el proyecto
  ya usa Bootstrap Icons por CDN en todas las demás vistas
  (bi-calendar2-check-fill, bi-check-circle-fill, etc.) y cambiar de
  librería de íconos a mitad de la app es puro costo de mantenimiento
  sin beneficio para el usuario final.
- La interactividad en JavaScript plano (querySelectorAll + listeners
  manuales) del mockup se reemplaza por Alpine.js, que ya es una
  dependencia del proyecto (package.json) y es el patrón que Laravel
  recomienda para interactividad ligera sin montar un SPA completo.

30.3 Boceto
El boceto interactivo mostrado en esta conversación refleja la
estructura propuesta (tarjetas de estadísticas + tablero por unidad +
panel de detalle + incidencias) usando los colores reales del proyecto
(#0B3C78 / #7B1E2B) en vez de la paleta del mockup original. Es una
referencia de estructura y jerarquía visual, no el maquetado final: el
maquetado final en Blade debe conservar los componentes visuales que ya
existen en el proyecto (badges rounded-pill, sombras suaves, gradientes
en botones primarios) para no romper la coherencia con el resto del
sistema.

30.4 Implementación propuesta (alto nivel, respeta MVC)
- AsignacionTurnoController@index sigue devolviendo la vista; se agrega
  un método auxiliar en el Service (o un nuevo
  DashboardTurnosService) que arme el arreglo de unidades con sus
  segmentos de turno del día, para no meter esa lógica de agrupación
  en el Controller ni en la vista.
- La vista index.blade.php pasa a usar x-data de Alpine para manejar
  qué segmento está seleccionado y refrescar el panel de detalle sin
  recargar la página; los datos de cada turno se embeben como JSON ya
  calculado por el Controller (no se consulta la BD desde Alpine).
- El polling de respaldo o el WebSocket (secciones 15-17) actualizan
  únicamente el estado "en curso"/posición de las unidades ya
  pintadas; no reconstruyen el tablero completo en cada evento.
